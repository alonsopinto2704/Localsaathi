# Phase 012 — Threat model and abuse stories

**Status:** Done (gate passed in phase-020; human sign-off pending)

**Objective:** Model the realistic abuse paths against the Flutter + Supabase directory (and the planned Saathi AI) as they exist in code today; rank them by impact and exposure; give each a prevention control, a detection control, a concrete negative test, an owner role, an implementing phase and a residual-risk decision. No unrelated security products are proposed; every control is a Postgres grant/RLS/RPC change, an Edge Function, a Supabase Auth setting, or an operating procedure already implied by the roadmap.

## Content

### Trust boundary facts that drive the ranking

1. The client always runs the mock graph: `lib/main.dart:28,36` calls `AppDependencies.mock`; `lib/app/app_dependencies.dart:46` [audit-corrected] is the only factory. Server-side threats are therefore latent until Phase 061 wires live repositories, but the database is deployable today and anyone with the project URL and anon key can call it directly. Rate/abuse controls must exist before the first public deployment, not before the first Flutter release.
2. `grant execute on all functions ... to anon, authenticated` plus default privileges for future functions (`0009_rls.sql:16-17`) means every helper, trigger helper, and future function is a public RPC unless revoked (Phase 023).
3. Anon can SELECT the whole `provider_profiles` row for any published+active listing (`0009_rls.sql:71,73-75`). RLS filters rows; it does not hide columns (plan line 31).
4. Only `moderationStatus` is stripped from the public JSON (`0008_functions.sql:177`); everything else the builder emits is public, including `phoneE164` (`0008_functions.sql:90`), health-claim fields (`:138-147`) and, since `0012`, the map pin (`0012_map_location_and_terms.sql:91-104 [audit-corrected]`).
