### 2. Existing switches that must be reused (not duplicated)

- **Cities: `public.cities.launch_status` enum `active | coming_soon | inactive`** (`0002_locations.sql:27,33`). The column comment states it is "the whole mechanism for activating a new market" (`0002:60-63`). Seed: Mumbai `active`, all others `coming_soon` (`seed.sql:49-110 [audit-corrected]`). Today it is enforced in exactly one place: `register_profile` rejects non-active cities (`0008:437-443`, tested by `tests/database/0004_city_activation_and_deletion.test.sql`). It is not checked in `search_providers` (`0008:206-339`), `get_public_profile` (`0008:170`), `similar_providers` (`0008:343`), `provider_count_by_locality` (`0008:366`) or `providers_published_in_city` (`0008:672`). Phase 028 makes every route honour it and adds the audited, admin-only change path; this design reuses that and adds no per-city flag table. Writes to `cities` today go through `"only admins write reference data"` (`0009:44`).
- **Categories: `service_categories.is_healthcare` and `is_approved_for_launch`** (`0003_catalog.sql:24,26`). `is_approved_for_launch` is not read by any SQL function or policy (only the seed generator writes it: `backend/scripts/generate_seed_sql.py:194,202`). All seeded healthcare categories are `true` for `is_approved_for_launch` and `true` for `is_healthcare` (`seed.sql`, e.g. `general-physician`), so the healthcare category is effectively live in the data. Reuse `is_approved_for_launch` as the per-category gate and add one global flag for the whole healthcare vertical.
- **Client constants are not flags.** `AppConfig.useDevelopmentOtpSimulation`, `engagementStatsAreSampleData`, `legalTextReviewed`, `freePhotoLimit` (`app_config.dart:37,58,72,54`) are build-time values; they stay as release guardrails (Phase 287), not as server flags. `check_photo_limit` hard-codes `5` in SQL (`0004:223`).

### 3. Flag mechanism design (for later phases)

- **Storage:** table `public.feature_flags(key text primary key, enabled boolean not null default false, rollout jsonb not null default '{}', min_client_version text, reason text, updated_by uuid, updated_at timestamptz)`. `rollout` carries audience: `{"audience":"internal|cohort|all", "user_ids":[...], "cohort":"mumbai-ai-pilot", "pct":0-100}`. A missing row means disabled. No anon/authenticated table grants and no PostgREST exposure of the table.
- **Enforcement point (server, authoritative):** `public.flag_enabled(p_key text) returns boolean`, `stable`, `security definer`, `set search_path = ''`. It takes **only the key** and evaluates the audience for `auth.uid()` internally, so the one thing a caller learns is whether a capability is on *for themselves*; rollout lists and other users' cohorts are never readable. Privileges: `revoke execute ... from public` (naming PUBLIC explicitly; revoking only from anon/authenticated leaves EXECUTE via PUBLIC), then `grant execute ... to anon, authenticated`, because RLS/Storage policies and INVOKER triggers run as the caller and fail with 42501 `permission denied for function` if the caller cannot execute a function they call (executed in the Phase 017 audit; same rule that keeps `is_admin()` executable, phase-013 Rec 1). The `feature_flags` table itself has no anon/authenticated grants. Preferred placement: gated **writes** check the flag inside their SECURITY DEFINER RPC (direct table writes are already revoked since migration 0013), so policies only need `flag_enabled` for gated **reads** (e.g. a Storage bucket). Edge Functions read the same table with the service-role key and cache for at most 60 s. **Fail closed:** read error or missing row = disabled for the gated capability; core capabilities never depend on a flag read.
- History: the first draft revoked EXECUTE from `anon`/`authenticated` while also calling the function from policies; the independent audit below proved that fails (42501). The design above replaces it.
- **Client hint (UX only):** one public RPC `get_client_flags()` returns booleans for the caller (no rollout details), so the app can hide entry points. The app must treat it as a hint: server rejection (`feature_disabled`, a new error code alongside the existing `not_owner`/`location_not_active` family) is the real boundary. On fetch failure the client shows last known good for hiding, never for enabling.
- **Change control:** only an audited admin RPC `set_feature_flag(key, enabled, rollout, reason)` writes the table; reason mandatory; each write appends to the Phase 036 append-only audit. Environment-labelled in the admin surface (Phase 241). Not carried in JWT claims, so a flip takes effect on the next request (within the 60 s Edge cache).
- **Rollback:** "disable one capability without rolling back the app" (Phase 017 safe-stop) is one `set_feature_flag(..., false, reason)` call; data is preserved, never deleted by a flag flip.
- **Test pattern for every flag:** (1) with the flag off, the endpoint returns `feature_disabled` for an authorised caller, (2) the same call works with it on, (3) every core path still works with it off, (4) a direct table or Storage call that bypasses the UI is also rejected. These belong in the Phase 039 HTTP regression pack and Phase 264 CI.

### 7. Disposition rule for the release owner

For a gate that depends on a flagged capability, a "Deferred / feature disabled" record is acceptable only if it names the disabled UI, endpoints, jobs and flag, and a test proves the server rejection (plan lines 116-118). It is not acceptable for authorization, deletion, legal disclosure, signing or recovery (plan line 116).

## Residual uncertainty

- No flag mechanism exists today, so every "behaviour when disabled" entry is a proposal; none was tested. The Supabase facts used (policies may call functions; Edge Functions can use the service role) are standard but not verified in a live project here.
- `is_approved_for_launch` is unread by SQL; whether the Flutter catalog should also respect it, and how to treat already-published healthcare listings when the flag turns off, is a product decision (this design hides them, never deletes them).
- Whether `media_intake` ships ON for the first release is a launch-scope choice for the product lead; this design recommends OFF unless 083/084 are evidenced.
- Fail-closed means a flag-store outage disables optional features, not core; that tradeoff is accepted here but should be confirmed in Phase 275 (dependency-failure exercises).
- The 60-second cache bound is a suggestion; if instant kill is needed for `contact_reveal`, shorten it for that flag.
